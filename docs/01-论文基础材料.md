# 论文基础材料包（第1包）

## 1. 项目定位与系统简介

农产品溯源管理信息系统是一个面向毕业设计、答辩演示和后续扩展的轻量级农产品溯源系统。项目不追求复杂大平台，而是围绕“产品建档、批次创建、现场记录、质检确认、二维码发布、公众查询、风险处理、监管查看”建立一条清晰可演示的业务闭环。系统以“批次”为核心业务对象，把企业、产品、过程记录、质检报告、二维码和风险状态串联起来，使后台管理链路和消费者扫码查询链路能够相互对应。

系统采用三端结构：`backend` 是 Spring Boot 后端服务，负责认证、权限、批次、产品、企业、质检、风险、二维码、公开追溯等接口；`admin-web` 是 Vue 管理端，面向平台管理员、企业管理员、现场操作员和监管人员；`trace-web` 是 Vue 公开追溯端，面向消费者或答辩评审，通过公开 token 查询批次追溯信息。

本文档在系统名称、论文正文和章节表述中统一采用“溯源”口径；涉及现有页面、接口或消费者侧功能命名时，保留项目中已有的“公开追溯查询”“公开追溯端”“追溯时间线”等表述，避免与本地实现名称脱节。

系统核心目标是用较少页面和较清晰的操作路径完成真实业务演示：后台能管理批次，现场能补录过程，企业能质检和发布，公众能扫码查询，风险状态能联动公开页，监管人员能只读审查。

## 2. 核心功能模块

产品建档：用于维护农产品基础资料，例如产品编码、名称、类别、产地、规格、单位、图片等。产品是批次创建的前提，一个产品可以关联多个生产或流转批次。

企业主体管理：用于维护企业主体档案，包括企业名称、许可证号、地址、联系人、联系电话和启停状态。当前后台路由中企业相关管理主要面向平台管理员和企业管理员，更贴合“建档 -> 批次 -> 过程 -> 质检 -> 发布”的业务主链路。

批次管理：用于创建、查询和维护具体批次，是系统最核心的业务模块。批次关联企业和产品，并承载任务状态、质检状态、发布状态、风险状态和公开追溯入口。

现场溯源记录：用于记录生产、采收、分拣、冷链、入库、发运等过程节点。当前实现中过程事件存放在 `trace_event`，现场草稿能力对应 `batch_field_draft`。

质检管理：用于记录批次质检报告、检测机构、报告编号和检测结论。质检结果是批次发布和公众可信展示的重要依据。

二维码生成与发布：用于给批次生成公开查询 token 和二维码。当前核心数据对象是 `qr_code`，公开追溯端通过 token 查询对应批次。

公开追溯查询：面向消费者或答辩评审，不需要登录后台。公开端路由为 `/t/:token`，通过后端 `GET /api/public/traces/{token}` 获取批次追溯详情。

风险处理与监管查看：风险处理用于冻结、召回、整改、恢复等异常状态管理，当前风险动作存放在 `batch_risk_action`。监管角色在后台以只读方式查看批次、质检和风险，不作为直接改写业务数据的角色。

## 3. 系统角色与职责

`PLATFORM_ADMIN`：平台管理员，负责全局总览、批次查看、企业管理、产品管理、用户管理、日志查看、质检与风险链路检查等工作。主要入口是管理端 `/dashboard`，也可以进入 `/products`、`/companies`、`/users`、`/logs`、`/batches`、`/quality`、`/risk`、`/qr` 等页面。

`ENTERPRISE_ADMIN`：企业管理员，负责本企业范围内的产品、批次、质检、二维码发布和风险处理相关操作。主要入口是管理端 `/batches`，适合围绕本企业批次工作台讲解业务闭环。

`OPERATOR`：现场操作员，负责被分配批次的现场记录补录、草稿保存、续写和提交。主要入口是管理端 `/field-entry`，偏向一线填报场景，不承担全局后台管理职责。

`REGULATOR`：监管人员，负责只读查看批次、质检和风险信息，审查链路完整性和异常处理进度。主要入口是管理端 `/risk`，当前路由和 e2e 用例都强调其只读边界。

消费者：消费者不是后台登录角色，不在 `admin-web` 角色枚举中。消费者通过 `trace-web` 的公开地址 `/t/:token` 查询追溯信息，用于查看产品来源、批次状态、关键时间线、质检结论和风险提示。

## 4. 业务主链路

1. 登录后台：平台管理员、企业管理员、现场操作员或监管人员进入 `admin-web` 登录页，通过 `POST /api/auth/login` 完成身份认证。
2. Dashboard：平台管理员和企业管理员可查看首页总览，理解系统中批次、发布、风险、扫码等整体情况。
3. 产品/企业建档：平台管理员或企业管理员维护企业主体和产品档案，为批次创建提供基础数据。
4. 批次创建：企业管理员围绕已有产品创建具体批次，批次成为后续追溯事件、质检、二维码和风险动作的主对象。
5. 批次工作台：用户进入批次详情或工作台，集中查看批次状态、负责人、任务状态、质检状态、风险状态和公开链接。
6. 现场填报：操作员在 `/field-entry` 对分配批次补录现场记录，可形成草稿或提交为正式追溯事件。
7. 质检：企业管理员或具备权限的后台角色录入质检报告和检测结论，形成批次是否具备公开发布条件的重要依据。
8. 二维码生成与发布：后台为批次生成二维码和公开 token，并将批次与公开查询入口绑定。
9. 公开页查询：消费者或答辩评审访问 `trace-web` 的 `/t/:token`，查看批次追溯摘要、关键时间线、质检结果和风险提示。
10. 风险处理：当批次出现异常时，后台可记录冻结、召回、处理中、整改等动作，公开页根据批次或二维码状态展示对应风险提示，监管人员可进行只读审查。

## 5. 核心数据对象与数据库线索

当前系统中“批次”是核心数据对象。产品和企业提供基础档案，批次将某个企业、某个产品和一次具体生产或流转活动绑定起来。溯源事件记录批次生命周期中的过程节点，质检报告记录批次质量依据，二维码记录批次公开查询 token，查询日志记录公众访问行为，风险动作记录冻结、召回、整改等异常处理过程。

当前实现优先采用 `backend/src/main/resources/schema-demo.sql` 作为数据库结构说明依据。该文件是 demo profile 实际使用的 H2 表结构，包含 `org_company`、`sys_user`、`operation_audit_log`、`base_product`、`trace_batch`、`trace_event`、`batch_field_draft`、`quality_report`、`biz_attachment`、`qr_code`、`qr_query_log`、`batch_status_log`、`batch_risk_action` 等表。

`docs/database/sql/01_schema.sql` 可作为扩展设计参考。它是历史整理的 MySQL 结构，包含一些当前 demo 表结构没有直接启用或不作为主线实现依据的扩展表，例如 `consumer_feedback`、`hash_notary`、`invite_code`、`pesticide_record`、`regulation_record`、`regulator_org`、`trace_batch_participant`、`qr_query_stat_day` 等。论文写当前实现时应以 `schema-demo.sql` 为准，写后续扩展时再引用 `docs/database/sql/01_schema.sql`。

## 7. 论文可直接引用的表述

系统简介段：本文设计并实现了一个轻量级农产品溯源管理信息系统，系统围绕农产品从建档、批次创建、过程记录、质检确认、二维码发布到公众查询和风险处理的业务链路展开。系统采用后端服务、管理端前端和公开追溯端前端的三端结构，其中后端负责接口、数据和权限控制，管理端面向平台、企业、操作员和监管角色提供业务操作入口，公开追溯端面向消费者提供扫码查询页面。系统以批次为核心对象，将企业、产品、过程事件、质检报告、二维码和风险状态统一组织，形成可演示、可验证、可扩展的溯源闭环。

角色说明段：系统后台主要包含平台管理员、企业管理员、现场操作员和监管人员四类角色。平台管理员负责全局管理和系统运行查看，企业管理员负责本企业产品、批次、质检、发布和风险处理，现场操作员负责被分配批次的现场记录填报，监管人员以只读方式查看批次、质检和风险信息。消费者不属于后台登录角色，而是通过公开追溯端访问 `/t/:token` 查询批次信息，从而查看产品来源、批次状态、追溯时间线、质检结论和风险提示。

主业务流程段：系统主业务流程从后台登录开始，管理员首先通过 Dashboard 查看整体情况，再维护企业和产品基础档案，并围绕已有产品创建批次。批次创建后进入批次工作台，现场操作员补录生产、分拣、冷链等追溯记录，企业侧录入质检报告并确认质量结论。满足发布条件后，系统为批次生成二维码和公开 token，消费者通过公开追溯页查询批次信息。当批次出现异常时，后台记录冻结、召回或整改等风险动作，公开端同步展示风险提示，监管人员可从只读视角审查处理过程。

数据对象说明段：系统数据模型以批次为中心，企业和产品为批次提供基础归属关系，溯源事件记录批次生命周期中的关键过程，质检报告提供质量判断依据，二维码表保存批次对外公开查询 token，查询日志记录公众访问情况，状态日志和风险动作表记录批次状态变化和异常处理过程。当前实现的数据库结构以 `schema-demo.sql` 为准，该结构覆盖了演示闭环所需的核心表；历史 MySQL 脚本 `docs/database/sql/01_schema.sql` 可作为后续扩展设计参考。

## 8. 已发现的信息冲突与采用口径
