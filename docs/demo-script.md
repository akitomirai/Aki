# 答辩演示脚本

## 1. 项目一句话介绍

这是一个面向农产品批次管理、过程追溯、质检发布、风险处理和消费者扫码查询的多角色追溯系统。

## 2. 系统角色说明

- 平台管理员
  - 适合演示全局总览、产品与批次管理、用户与企业管理、日志查看、风险与质检链路。
- 企业管理员
  - 适合演示本企业视角下的批次管理、工作台、质检与发布操作。
- 企业操作员
  - 适合演示现场填报、任务处理、草稿与提交。
- 监管方
  - 适合演示只读访问、风险查看、禁止写操作的权限边界。
- 消费者
  - 不需要登录，直接通过公开追溯页查看批次状态、来源、质检和关键过程信息。

当前仓库中稳定可用的演示账号与入口以本地脚本和基线回归为准：

- `platform / 123456`
- `enterprise_admin / 123456`
- `operator / 123456`
- `regulator / 123456`
- 公开追溯页：`http://127.0.0.1:5173/t/orange-202603-d1`

## 3. 答辩时建议启动方式

推荐直接使用仓库现有本地脚本，不要临时手动拼命令。

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\stop-local.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\check-local.ps1
```

如果答辩前还想做一次带登录态的后台预检查，可补跑：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\demo-precheck.ps1
```

如果答辩当天需要证明整条链路已经真实验证过，可补充说明主回归入口：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run-baseline-regression.ps1
```

## 4. 演示前检查项

- 确认三个服务都已启动：
  - backend：`http://127.0.0.1:8080/actuator/health`
  - admin-web：`http://127.0.0.1:5174/login`
  - trace-web：`http://127.0.0.1:5173/t/orange-202603-d1`
- 准备两个浏览器页签或两个窗口：
  - 一个用于后台管理端
  - 一个用于公开追溯页
- 优先使用 `platform` 账号演示主链路，因为它能看到最完整的页面与模块。
- 如果要切换监管视角，单独使用 `regulator` 登录，避免和平台账号混淆。
- 演示主对象尽量固定在 clean baseline 批次：
  - 批次编码：`ORANGE-202603-D1`
  - 公开追溯地址：`http://127.0.0.1:5173/t/orange-202603-d1`
- 如果老师更关注“系统是否真的跑通过”，可提前打开冻结基线文档：
  - `docs/baselines/2026-04-02-clean-baseline.md`

## 5. 推荐演示顺序

### 第一步：登录后台

- 打开 `http://127.0.0.1:5174/login`
- 使用 `platform / 123456` 登录

老师能看到什么：

- 系统不是静态页面，而是有真实登录、角色和权限边界的后台。

为什么有价值：

- 说明系统不是单一页面展示，而是面向真实角色使用的业务系统。

### 第二步：查看 Dashboard

- 进入 `/dashboard`
- 先讲清楚系统核心对象是“产品、批次、任务、质检、风险、公开追溯”

老师能看到什么：

- 后台总览页和系统整体运营视角。

为什么有价值：

- 能快速让老师建立整体认知，知道这不是零散 CRUD，而是围绕追溯链路组织的系统。

### 第三步：查看产品、批次和工作台

- 打开 `/products`
- 打开 `/batches`
- 进入批次工作台 `/batches/2`

老师能看到什么：

- 产品是静态档案。
- 批次是业务主线对象。
- 工作台汇总了批次状态、任务状态、质检状态、风险状态、公开链接等核心信息。

为什么有价值：

- 体现“以批次为中心”的系统设计。
- 老师能直接看到一个批次从创建到发布再到对外展示的核心入口已经被整合到工作台。

### 第四步：讲任务、现场填报、质检和风险链路

- 先在批次工作台说明任务分配和任务状态。
- 再说明企业操作员入口是 `/field-entry`，用于现场记录与草稿提交。
- 再打开 `/quality` 说明质检结果如何进入批次。
- 再打开 `/risk` 说明冻结、处理中、已整改、恢复发布等风险状态链路。

老师能看到什么：

- 批次不是只有“创建”和“查看”，而是有任务、过程记录、质检、风险联动的一整条链路。

为什么有价值：

- 这是系统最能体现“闭环”的部分。
- 能说明后台不是纯台账，而是支持过程录入、质量判断和异常处理。

### 第五步：生成或查看追溯码

- 打开 `/qr`
- 说明二维码和公开追溯地址绑定到具体批次

老师能看到什么：

- 批次与追溯码、公开链接之间的对应关系。

为什么有价值：

- 这一步把后台业务与消费者扫码入口真正连起来了，是“追溯系统”区别于普通管理系统的关键价值。

### 第六步：消费者扫码查看追溯页

- 打开 `http://127.0.0.1:5173/t/orange-202603-d1`
- 按“首屏摘要 -> 关键过程 -> 质检状态 -> 风险状态”的顺序讲

老师能看到什么：

- 消费者不需要登录，就能直接看到批次状态、来源、最新记录和风险提示。

为什么有价值：

- 能体现系统最终对外价值。
- 老师更容易理解“这套系统不是只给管理员看，而是最终面向消费者建立信任”。

### 第七步：监管只读查看

- 退出平台账号，使用 `regulator / 123456` 登录
- 推荐打开 `/risk`、`/batches`、`/quality`

老师能看到什么：

- 监管角色可以查看关键页面，但不能进行写操作。

为什么有价值：

- 能体现角色隔离与权限控制。
- 结合当前回归 smoke，可以说明监管方链路不是口头设计，而是已经被真实验证。

## 6. 每一步老师能看到什么，为什么能体现系统价值

| 演示环节 | 老师直观看到的内容 | 系统价值 |
| --- | --- | --- |
| 登录后台 | 真正的登录页、角色边界 | 说明系统不是静态原型 |
| Dashboard | 后台总览和核心模块入口 | 快速建立整体认知 |
| 产品与批次 | 产品档案 + 批次主线 | 强调“以批次为中心” |
| 工作台 | 状态、任务、质检、风险、公开链接聚合 | 说明链路整合度高 |
| 现场填报 | 操作员任务、草稿、提交入口 | 体现一线录入场景 |
| 质检与风险 | 合格/不合格、冻结/整改/恢复发布 | 体现异常处理能力 |
| 追溯码与公开页 | 扫码后直接看到真实批次信息 | 体现对消费者的最终价值 |
| 监管只读 | 只读查看、禁止写入 | 体现权限控制与监管视角 |

## 7. 演示时避免踩坑事项

- 不要把答辩现场第一步变成重新开发或排障，优先使用现成脚本。
- 不要一上来就切多个账号，先用 `platform` 讲主链路，再单独切 `regulator`。
- 不要临时修改 `ORANGE-202603-D1` 的基线数据结构，优先展示现成稳定链路。
- `trace-web` 根地址会跳转到默认 token，答辩时最好直接打开稳定地址 `/t/orange-202603-d1`。
- `operator` 角色默认更适合展示 `/field-entry`，不适合拿来展示后台总览。
- `regulator` 是只读角色，答辩时不要期待它有写按钮。
- 如果老师追问“这个 400 为什么出现”，可以解释为预期业务拦截：
  - 改派前如果当前分配人还有未提交草稿，系统会先阻断并要求确认，这属于 clean baseline 中的 `Expected intercepts`，不是异常失败。
